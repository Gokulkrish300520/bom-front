
# Django REST API: Complete Usage Guide (2025)

## Project Structure (Updated)
- Modular Django apps: core, banking, etc.
- All business logic is atomic and auditable
- All endpoints require JWT authentication
- Full test coverage, all tests discoverable from project root
- Linter score: ~95% (see flake8_report.txt)



## 1. Running the Server
- Install dependencies:
    pipenv install --dev
- Apply migrations and start the server:
    python manage.py migrate
    python manage.py runserver
- The server will be available at http://localhost:8000/

## 1b. Running Tests and Linter
- Run all tests from project root:
    PYTHONPATH=$(pwd) DJANGO_SETTINGS_MODULE=server.server.settings pipenv run python3 -m django test
- Run linter (excluding migrations):
    pipenv run flake8 server/core --exclude=migrations


## 1a. Filtering Endpoints by customer_id and vendor_id

Many list endpoints support filtering by `customer_id` and/or `vendor_id` via query parameters. This allows you to retrieve only the records related to a specific customer or vendor.

### Supported Endpoints
- Quotes: `/api/quotes/?customer_id=<id>`
- Invoices: `/api/invoices/?customer_id=<id>`
- Proforma Invoices: `/api/proforma-invoices/?customer_id=<id>`
- Delivery Challans: `/api/delivery-challans/?customer_id=<id>`
- Bills: `/api/bills/?vendor_id=<id>`

### Usage Examples

- List all invoices for a customer:
    `GET /api/invoices/?customer_id=1`

- List all bills for a vendor:
    `GET /api/bills/?vendor_id=2`

- List all quotes for a customer:
    `GET /api/quotes/?customer_id=3`

You can combine these filters with other query parameters as needed. Filtering is robust and works with pagination and ordering.

## 2. User Management (Admin Only)
- Create a superuser:

    python manage.py createsuperuser

- Visit http://localhost:8000/admin/ and log in.
- Add users via the Django admin interface (no public registration endpoint).


## 3. Authentication (JWT)
- Obtain a JWT token:
    POST /api/auth/token/
    {
        "username": "<username>",
        "password": "<password>"
    }
- Response:
    {
        "refresh": "<refresh_token>",
        "access": "<access_token>"
    }
- Use the access token in the Authorization header for all API requests:
    Authorization: Bearer <access_token>

#### Vendor Fields
- vendor_type: "business" or "individual" (default: business)

- contact_persons: array of ContactPerson objects (see below)
- custom_fields: object (optional)
- tags: array (optional)
- remarks: string (optional)
- created_at: datetime (read-only)
- id: integer (read-only)

#### Example: Update Contact Persons (retain, add, remove)

To update contact persons for a customer, make a PUT request to `/api/customers/{id}/` with the full customer data, including the `contact_persons` array. The update logic is as follows:

- If a contact person in the array has an `id` matching an existing contact person, that contact person will be updated in place (ID retained).
- If a contact person in the array does not have an `id`, a new contact person will be created.
- Any existing contact person not included in the array will be deleted.

**Example:**

PUT /api/customers/1/
Content-Type: application/json
Authorization: Bearer <access_token>

{
    "display_name": "Acme Corp (Updated)",
    "email": "john.doe@acme.com",
    "customer_type": "business",
    "company_name": "Acme Corp",
    "currency": "INR",
    "payment_terms": "net_30",
    "contact_persons": [
        {"id": 1, "salutation": "ms", "first_name": "Jane", "last_name": "Smith", "email": "jane@acme.com", "work_phone": "", "mobile": ""},
        {"first_name": "New", "last_name": "Person", "email": "new@acme.com", "work_phone": "", "mobile": "", "salutation": null}
    ]
}

**Result:**
- Contact person with `id: 1` is updated in place.
- A new contact person is created for "New Person".
- Any other contact persons previously associated with the customer are deleted.

### Invoice File Attachments

There are two ways to attach files to an Invoice:

1. **General attachments**: Use the `attached_file_ids` field to associate general files with the invoice (these may be uploaded via the UI or other means).
2. **Invoice-specific attachments**: Use the `invoice_file_ids` field to associate files specifically as invoice documents.

Both fields are write-only for input. The response will include `attached_files` and `invoice_files` arrays with file metadata.

**Example: Attach files by ID (programmatic)**

```
POST /api/invoices/
{
    ...
    "attached_file_ids": [4, 5],
    "invoice_file_ids": [1, 2, 3]
}
```

**Note:**
- `files` and `invoice_file_ids` are distinct. `files` is for uploading new files; `invoice_file_ids` is for attaching existing files.
- Both fields can be used independently or together as needed.

### Profit and Loss Report
- GET /api/reports/profit-and-loss/?time=This%20Month|Last%20Month|This%20Year&basis=Accrual|Cash&compare_with=None|Last%20Month|Last%20Year
- Returns a real-time Profit and Loss report for the specified period, basis, and optional comparison.
- Requires authentication (JWT access token).

#### Query Parameters
- time: string (This Month, Last Month, This Year; default: This Month)
- basis: string (Accrual or Cash; default: Accrual)
- compare_with: string (None, Last Month, Last Year; default: None)
- customer_id: integer (optional)
- summary_only: boolean (optional, default: false). If true, omits invoice_breakdown and bill_breakdown for faster summary-only response.

- cost_of_goods_sold: Total bill amount (COGS) for the period

- non_operating_income: (currently 0)
- non_operating_expense: (currently 0)
- net_profit_loss: operating_profit + non_operating_income - non_operating_expense
- payments_received: Total payments received for the period
- invoice_breakdown: List of invoices in the period
- bill_breakdown: List of bills in the period

## 6. Background Pre-Aggregation (Performance Optimization)

### DailySummary Table
- The system maintains a `DailySummary` table with daily totals for invoices, bills, and payments.
- This is updated automatically every 24 hours using a background task (django-background-tasks).
- You can also trigger pre-aggregation manually from the Django admin (DailySummary > Actions > Run daily pre-aggregation now).

### How it works
- On Django startup, the background task is scheduled if not already present.
- The task runs every 24 hours and updates/creates daily summary rows for all dates in the data.
- You can also run the task manually from the admin or by calling `python3 manage.py process_tasks` in a terminal.

### Monitoring
- The `DailySummary` table is visible in the Django admin for review and manual triggering.
- The background task queue can be monitored with `python3 manage.py process_tasks` (should be running in production).

### Dependencies
- Uses the `django-background-tasks` package for scheduling and running background jobs.
